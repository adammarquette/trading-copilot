## 1. Architecture Patterns

The runtime is a **.NET backend-for-frontend (BFF) / sidecar hosting an agent orchestrator**, with a thin local UI as its client. (Requirement IDs like R-5/R-12 refer to the PRD; the service topology is in the [architecture doc](trading-platform-architecture.md).) The core patterns:

- **BFF with an agent orchestrator.** An always-on .NET service hosts the suggestion agent, tool routing, the execution gate, and the API the local UI consumes. The UI is a thin client of the BFF.
- **In-process tool layer.** The agent calls data / analytics / journal / rulebook / broker (`MarqSpec.Client.ProjectX`) / TradingView as tools through a **contract-validated, audited in-process tool seam** — same invocation pattern per tool, not the MCP wire protocol.
- **Verify-before-act.** A verification layer checks a proposed action against ground truth *before* it happens. For orders that is the **R-5 risk gate + R-12 execution-time re-validation + R-16 sanity caps** — nothing reaches the broker unverified. Rules evaluate structured tool results (not model prose) and can **hard-block**: a fired rule stops transmission.
- **Real-time push is durable, not best-effort.** Server-initiated state and alerts ride an **outbox +
  monotonic-sequence + idempotent-resume** pattern, so a client that drops resumes without gaps or replays
  ([ADR-0006](adr/0006-multi-screen-workspace.md)) — the property that lets a detached panel be trusted after a
  reconnect. *The transport and what it carries: §2.*
- **Railway deployment.** The always-on cloud tier (ingestion, analytics, agent, execution, storage) deploys to Railway.
- **Observability.** OpenTelemetry → self-hosted **Prometheus + Loki + Tempo + Grafana** (the LGTM stack — metrics / logs / traces), plus execution-specific signals (order-gate pass/block, auto-flatten success, time-to-flat, order-ack latency). Auto-flatten reliability is a monitored, alertable metric.
- **Secrets server-side.** Broker credentials and API keys live only in the cloud tier's secret storage; the local UI never holds them.

**Net-new, safety-critical:** the **execution + auto-flatten layer** — order gate, kill switch, the redundant flatten guarantee, and the practice/live mode surface — is a from-scratch build held to the highest bar (§9), designed with the same verify-before-act rigor as the rest of the system.

**The UI is a React SPA client** against the remote BFF — a single-origin client that authenticates to the API with a **JWT bearer token** (REST + SignalR; §2), not embedded in any other app. Bearer tokens sidestep cross-site-cookie concerns entirely.

## 2. Tech Stack & Platform

The stack below is the settled default; diverge only with a reason.

- **Runtime/language:** .NET 10 (LTS), C# latest, `Nullable` on, warnings-as-errors — solution-wide via `Directory.Build.props`.
- **Host / API:** ASP.NET Core BFF (the always-on cloud tier); the local UI is a thin client of it.
- **Real-time:** SignalR — reused for chat *and* for pushing order/fill/position state, proactive alerts, and flatten warnings (R-6, R-10, R-11, R-13). Server-initiated push uses `IHubContext` with per-user targeting on an **outbox + monotonic-sequence + idempotent-resume** durability pattern.
- **Frontend:** a **React SPA** — the operator's workspace (charts, suggestions, order/execution panel, journal, rulebook; R-6, R-10, R-11) — consuming the BFF's **REST** endpoints and the **SignalR** hubs (websockets) for real-time. **Ships as an installable PWA** (web-app manifest + service worker; **Android/Chromium** primary, **iOS/Safari** best-effort via Add-to-Home-Screen) — presentation only, so safety stays server-side (R-19, [ADR-0010](adr/0010-progressive-web-app.md)). **UI E2E Testing:** Playwright for automated browser/PWA testing once the SPA lands.
- **UI design language — dark-first Material, adaptive (ADR-0005).** The SPA uses **Material Design (Material 3)** as its component + interaction language, **dark theme first** (a light variant is a later **token** swap, not a redesign). Layout is **adaptive** on Material's window size classes — **compact / medium / expanded** — with **adaptive navigation** (bottom bar → icon rail → labelled navigation rail) and docks that reflow (panels → tabs → single column). A **token system** (surfaces + tonal elevation, one accent, type) drives theming; **semantic trading colors** (long/short, warn, critical) stay **separate from the accent** so status never competes with brand. **Roboto / Roboto Mono** with **tabular numerals** for prices/P&L. Two **safety controls are persistent at every breakpoint** — the **time-to-flat countdown** (R-13) and the **kill switch**. Wireframes: [`design/`](design/). **Decide:** the concrete React component library (**MUI / Material UI** the likely fit) + version (CPM).
- **Multi-screen workspace (ADR-0006).** The SPA supports **detachable pop-out panels** (`window.open`) spread across monitors, plus **workspace-per-window** layout presets — **web-native, no desktop install** — *the ADR argues why.* Live data stays consistent because **each window is just another SignalR client** on the existing outbox + monotonic-sequence + idempotent-resume backbone; **BroadcastChannel** syncs same-origin **UI** state (linked instrument/crosshair, layout, theme) without server round-trips; the **Window Management API** (where supported — Chromium, permissioned) auto-places windows, with manual drag as the fallback. **Execution stays single-authority server-side** — multi-window is a view concern, never a second order path — and the kill switch + countdown appear in every window. **Decide:** layout-preset persistence + cross-window token/session sharing (R-18).
- **Charting — the central UI component (R-10, ADR-0004):** the central candlestick chart is **TradingView Lightweight Charts** — native feel, canvas performance for tick data, Apache-2.0; **panes** carry the indicator **subcharts** (RSI, MACD, …), and it renders our **pre-computed** indicator series (ADR-0001), price lines, and markers as **overlays**, including custom indicators. Hand-drawing is out of scope. (KLineCharts is the documented fallback.) **d3 / canvas** handles lighter bespoke views (footprint, volume profile), never the main chart.
- **Order flow & Depth-of-Market — a bespoke component, later feature (R-3, R-1, ADR-0004).** A "Bookmap-style" real-time **time × price liquidity heatmap + trades** is *not* provided by any candlestick library; it's a dedicated **canvas / WebGL** component (SVG/d3 can't sustain the density) fed by ProjectX's `GatewayDepth` (DOM) + `GatewayTrade` streams — the webstream already provides the **trade-volume** data these displays need. **Deferred:** not Phase 1; lands with order-flow work (Phase 3, "an option"). **Spike:** §12.
- **API auth:** **JWT bearer** tokens on the REST API and the SignalR connection (the Internet-exposed surface, R-18). Tokens verified server-side; **authorization runs through a claims / policy layer**, not hard-coded single-operator checks, that **scopes every request to the authenticated identity** — data access is scoped so a forgotten scope returns nothing, a **default-deny safety property** on a single-operator deployment rather than tenancy (R-20, [ADR-0017](adr/0017-single-operator-data-isolation.md)); the policy layer keeps richer roles an incremental add ([ADR-0003](adr/0003-authentication.md)). **Decide:** token issuance/refresh, operator account lifecycle (credential rotation, deletion → R-15) — **not** registration, which a seeded single operator does not need — + where the signing key lives (server-side secret, §8).
- **External HTTP:** **typed `HttpClient`s registered through `IHttpClientFactory`** — deliberately hand-rolled, no SDK. Every external client the app itself owns is built this way (`AnthropicLlmProvider` gh#423, `CohereEmbeddingProvider` gh#403, `PushoverNotificationChannel`, and the Finnhub / Tiingo news sources gh#439/#440), for the same reason each time: permissive-licence and dependency-minimal, with the failure mapping explicit and fail-closed rather than inherited from a library. *(Refit is used **inside** the `MarqSpec.Client.ProjectX` submodule — a separate repo with its own choices — not in this solution. `Microsoft.Extensions.Http.Resilience` / Polly is **not** referenced anywhere today; per-client timeouts and fail-closed handling stand in. Adopting a resilience pipeline is open.)*
- **LLM access:** a hand-built `ILlmProvider` seam — Anthropic behind the seam in v1; no off-the-shelf LLM/MCP SDK. **Landed** (gh#402): the seam ships as `ILlmProvider` (provider-neutral text-in/out; `LlmUsage` + `LlmStopReason` on the completion so cost-tracking and fail-closed refusal handling are a fill-in for the real client, not a reshape). The **agent-review** reviewer calls it once per trigger fire. **Landed** (gh#423): the real **`AnthropicLlmProvider`** — a raw `HttpClient` adapter (no SDK; permissive-licence + dependency-minimal, mirrors the Pushover channel), one POST to the Messages API, key on the `x-api-key` header (never body/log), fail-closed on any non-2xx / bad body → `ReviewerUnavailable`. **Model tiers settled** — `Triage → claude-haiku-4-5`, `Deep → claude-sonnet-5`, operator-overridable via `LlmOptions`. Bound only when a key is present; the **stub** now stands in **only when unconfigured**, and ships **inert** (activated by the operator's key in `.env`). **Landed** (gh#431): the reviewer records a per-call `AIUsage` row (tokens / est. cost / latency / outcome) under the firing owner's scope — the LLM half of the spend signal, a **floor**. **Landed** (gh#448): the **platform-level AI-spend governor** — a pure gate mirroring the R-5 daily risk governor that caps agent-review LLM calls against the operator's daily budget (opt-in `GovernorOptions`, a Central-trading-day window). It enforces on the `AIUsage` ledger floor (the aggregate meter is `System.Diagnostics.Metrics` export-only / not app-readable, so reconciliation is operator-side in Grafana; effective cap = budget + one in-flight call), **fail-closed on the cap** but **fail-open on an unreadable spend signal** — the deliberate inverse of the fail-closed trade-safety gate, since it guards a budget, not capital. **Landed** (gh#478): the **budget-aware escalation skip** — the scan (which holds the tally) decides whether a triage→deep escalation still fits the budget and passes the reviewer a plain `allowEscalate` bit, so a deferred-but-unaffordable setup skips the expensive deep call and suppresses as `EscalationDeclined` (with an operator advisory) instead of overrunning. The reviewer stays **pure of the governor** — it gets a permission bit, never a budget, and only reports its own conservative deep-call cost estimate. **Landed** (gh#477): the **LLM-side meter**, so Grafana shows true total AI spend (§7). Still A2: a when-to-escalate eval suite. The **AI-invocation & cost model** — deterministic triggers do the continuous watching, the LLM is invoked **event-driven at the edges** (author triggers / review-on-fire / batched follow-ups), with cheaper-model triage and a spend cap — is recorded in [ADR-0008](adr/0008-ai-invocation-cost-model.md).
- **Persistence — one Postgres, three shapes (over EF Core):** **relational** (account/config, journal, orders/fills), **time-series via the TimescaleDB extension** (the bulk of the data — bars/ticks and other high-volume series, R-1), and **vector via pgvector** for **trading practices (the rulebook) and any data used for AI decision-making / retrieval**. TimescaleDB is chosen because much of the relational data is time-series.
- **Data layer:** entities and storage types live in **`MarqSpec.TradingCopilot.Data`** (`DbContext`, entities, migrations). **EF Core is the default** data-access path — reach for raw SQL only with a good reason (e.g. a proven hot-path performance need). **Schema changes go through `dotnet ef` migrations** (applied at startup); no ad-hoc schema drift. The data model is catalogued in **[`data-dictionary.md`](data-dictionary.md)** — kept in lockstep with the entities + migrations (update it in the same PR).
- **Embeddings & rerank — Cohere:** generates/optimizes the pgvector embeddings and reranks retrieval for **AI decision-making and chat** (behind `IEmbeddingProvider` / `IReranker` seams; hybrid dense + sparse retrieval). Start on Cohere's **free tier** (rate-limited); the **sparse-only fallback** covers rate-limit / outage / cost scenarios — not just an unset key — and paid tiers are available if usage grows (Q-10). **The embedding provider landed** (gh#403): `CohereEmbeddingProvider` behind the gh#109 seam, selected only when `Cohere__ApiKey` is set — an unset key keeps the keyless default and never crashes at first use. **Availability now means a key *and somewhere to put the vector*** (gh#474): `IsAvailable` is `IsConfigured && _vectorStore.IsPresent`, where `VectorStore` probes for the **pgvector** extension once at startup and defaults to *not* present — so a deployment with a key but no extension degrades cleanly to sparse instead of embedding at real cost and then faulting at the upsert every poll. It **degrades to sparse (returns null) rather than throwing** on a 429, outage, timeout, or a malformed response, so a retrieval call never takes an exception from a rate limit; only a genuine caller cancellation propagates. **Every call is metered** — tokens, estimated cost, latency, by model and outcome — including a failover, via the `MarqSpec.TradingCopilot.Ai` meter (below); an unmetered embed would be invisible spend on the operator's own key. Cost is estimated from a **single pinned rate** (`CohereOptions.UsdPerMillionTokens`). The seam rides each call's outcome + billed tokens back to the caller (`EmbeddingResult`, mirroring `LlmCompletion`), so a consumer can price and ledger every call — success or failure — **without reaching into a concrete provider's pricing**; that is the stack property. *Where those numbers go — the two-sink model (gh#436/gh#377), the `AIUsage` ledger and the governor's reconciliation — is §7.* Rerank is the separate, operator-gated `IReranker` stage (gh#103).
- **Config & secrets:** Options pattern with validate-on-start; secrets from environment/CI only, server-side (§8).
- **Cloud tier:** Railway (R-1 always-on) — project **`soothing-illumination`**; environments map to the `develop` / `staging` / `main` branches. Concrete resources + deploy/rollback procedures live in the **[deployment runbook](deployment-runbook.md)**. **Decide:** monthly cost ceiling (Q-10).

## 3. Solution & Repository Structure

- **Conventions:** `MarqSpec.TradingCopilot.<Area>` projects under `src/` (product + test projects co-located; `tools` later); `.slnx` solution; folder == project == root namespace; `I`-prefixed interfaces; source-generated logging in sibling `*Log.cs`.
- **Base namespace:** **`MarqSpec.TradingCopilot`** (decided, F1) — for consistency with `MarqSpec.Client.ProjectX`; projects are `MarqSpec.TradingCopilot.<Area>`.
- **Dependency management:** Central Package Management (`Directory.Packages.props`) — versions declared once, `.csproj` carries none. Respect license caps — pin **FluentAssertions `[6.12.0,8.0.0)`** (v8+ is commercially licensed).
- **Projects landed (F1→S4):** **`.Domain`** (the dependency-free core — the `Venue/` seam, `Risk/` gate, `Execution/` send path, `Flatten/` decision) · **`.Data`** (entities, `DbContext`, migrations) · **`.Api`** (BFF) · **`.Integration.ProjectX`** (the v1 venue adapter) · **`.Integration.Finnhub`** / **`.Integration.Tiingo`** (the data-only news adapters, gh#439/#440) · `.UnitTests` / `.IntegrationTests`. The originally-sketched `.Execution` / `.Risk` landed as **folders inside `.Domain`**, and market-data ingestion as a **`MarketData/` folder inside `.Api`**, not separate projects.
- **Forward sketch (Decide/refine as phases land):** `.Agent` (suggestion orchestrator) · `.Tools`/`.Mcp` (ProjectX, TradingView, journal, rulebook as agent tools — an *in-process, contract-validated tool seam*, not the MCP wire protocol) · `.MarketData` (ingestion + time-series) · `.OrderFlow` (tape/footprint/volume-profile analytics) · `.SoftSignals` · `.Journal` · `.Rulebook` · `.Llm` · `.Observability`. The **auto-flatten runtime (watchdog) is net-new / from scratch** (§1, §9).
- **Broker/venue abstraction (architectural goal — PRD R-17).** Market data, account state, and execution sit behind **venue-neutral interfaces**, with `MarqSpec.Client.ProjectX` as the v1 **adapter** — the same "one provider in v1, abstraction preserved" discipline used for the `ILlmProvider` seam. Broker-specific code lives only in a per-venue adapter project (e.g. `.Integration.ProjectX`; later `.Integration.Tradovate`); the engine, risk model, execution gate, journal, and UI depend on the abstractions. Instruments / accounts / orders / fills are **venue-tagged** end-to-end so risk, P&L, and the journal stay correct if accounts span venues, and venue capability gaps are explicit (an optional-capability / honest-empty pattern — a venue may not support every capability).
- **Data sources — providers vs. trading venues (extends R-17).** A **trading venue** (ProjectX, Tradovate) implements all three R-17 slices; a **data-only provider** implements just market data (and/or non-market data). *The slices and their interfaces are the architecture's §Venue abstraction.* **Finnhub** is the first data-only source — real-time **equities / indices** (SPY, QQQ, …) via **websocket** (free tier, ~50 symbols) + REST, used as **cross-asset context** for the futures we trade (SPY ↔ ES, NASDAQ/QQQ ↔ NQ), plus **alternative data** for AI-agent strategies (landing via the non-market-data template below). This opens **multi-asset ingestion** — futures + equities/indices + alt-data — through one pipeline. Equity **options** on watched symbols are a later, secondary use. Adapters implement each provider's **full API surface**, but **which feeds are *activated* is a wiring/config decision**. **Market/price data is single-source** — one provider owns it (Finnhub for equities/indices), so **Tiingo** (a second data-only provider) is built as a complete client yet **not wired for prices**, avoiding duplicate price data. **News is deliberately multi-source** — Finnhub news is **augmented by Tiingo**, both combined under the non-market-data template below with **cross-source dedup** (R-2). So "activated feeds" balances *no duplicate price data* against *broader, deduped news*. **Open:** Finnhub free-tier **data quality** — treat as unverified until checked. **Client repos scaffolded** (gh#383): `MarqSpec.Client.Finnhub` and `MarqSpec.Client.Tiingo` are pinned as **docs-only submodules** under `external/` following the venue-client pattern (ProjectX / Tradovate / Webull) — public, so CI's `submodules: true` checkout works without a cross-repo token. **Both news sources landed** (gh#439 Finnhub, gh#440 Tiingo): each a REST news client (token via header) + an `INewsSource` adapter in `.Integration.Finnhub` / `.Integration.Tiingo`, registered only when its `*__ApiKey` is set. With both keyed the poller fans in two news sources and dedups across them (R-2); Tiingo is wired for **news only**, so price data stays single-source (Finnhub).
- **Market-data ingestion — two paths, kept separate (R-1).** **Live**: ProjectX **websockets** (real-time ticks/quotes/trades), already implemented in `MarqSpec.Client.ProjectX`, feeding order-flow analytics (R-3). **Clean historical**: periodic **REST** backfill of OHLCV bars — the authoritative series read by journaling/replay (R-9). Don't conflate them: the live feed is not the historical system of record. The REST poll interval is user-configurable (**default 60s**, an env / Options setting for now; the final config surface is a system-design decision — §8).
- **Non-market data — one template, per-type adapters (R-2).** News, social (X), transcripts (YouTube), economic events, and future non-market feeds share **one model**: a per-type **source adapter** (in the poller fan-out) normalizes to a common schema, and the processor stores each item as a **structured / time-indexed row + a pgvector embedding** (Cohere) for semantic retrieval. **News is the reference implementation** — a new feed type is a new adapter, not a new pipeline. This is the non-market analog of the R-17 venue abstraction.

## 4. Coding Standards & Conventions

- **Baseline — Microsoft's C# coding conventions** (adopted from the dotnet/runtime + Roslyn styles): `PascalCase` types/members · `camelCase` locals · `_camelCase` private fields · `var` only when the type is obvious · language keywords over runtime types · **raw string literals** + `$""` interpolation · **collection expressions** `[…]` · target-typed `new()` · `required` over constructors · `Func<>`/`Action<>` · specific-exception catches · `using` declarations · **Allman braces, always** · **one public type per file** · `DateTime.UtcNow` never `.Now`. Full checklist + our deltas: **[wiki: .NET coding conventions](wiki/pages/dotnet-coding-conventions.md)**. Enforced by analyzers + a **checked-in root [`.editorconfig`](../.editorconfig)** + `dotnet format --verify-no-changes` + warnings-as-errors — style drift **fails the build**, not review.
- **Queries use fluent / method syntax — never LINQ query-comprehension.** Write `orders.Where(o => o.IsOpen).Select(o => o.Id)`, **not** `from o in orders where o.IsOpen select o.Id` — **everywhere queries are defined, EF Core included**. A deliberate deviation from the Microsoft samples (which show query syntax): the operator's standing preference — comprehension syntax pollutes the code; fluent chains read and compose better.
- **Standards:** file-scoped namespaces (enforced as a build *error*), immutability by default (`record`/`required`/`init`, `sealed` by default), **DI through the constructor only** (no static locators, no ambient state), async-all-the-way honoring `CancellationToken`, exhaustive `switch` on enums, `System.Text.Json` source-gen, **structured logging via `ILogger`** (message templates, never interpolation), XML docs on the public surface, terse comments with grep-able `reference:` pointers.
- **Domain primitives at the boundary (parse, don't validate):** `InstrumentId`, `AccountId`, and money/size types — errors here move real contracts.
- **Decide (trading-specific, early):**
  - **Money & prices:** `decimal`, tick-size-aware — **never** binary floating point for prices, sizes, or P&L.
  - **Time:** one canonical representation (UTC internally) with explicit CME/CT session boundaries and the **configurable flatten deadline (default ~2:30 PM CT, pre-MOC)** as first-class domain concepts.

## 5. Testing & Verification Strategy

Safety-critical system → testing is a first-class practice, not an afterthought.

- **Tiers:** **Unit** (fully mocked with FakeItEasy, no I/O, fast) · **Integration** (nothing mocked, against real deps in **staging**) · **Deterministic evals** for agent behavior (§6).
- **Frameworks (roles):** **xUnit** (test framework), **FakeItEasy** (mocking), **FluentAssertions** (assertions), coverlet (coverage). Honor the FluentAssertions `[6.12.0,8.0.0)` license cap.
- **Unit-test project & layout:** all unit tests live in one project, **`MarqSpec.TradingCopilot.UnitTests`**, with **one folder per product project, mirroring the namespace** — `MarqSpec.TradingCopilot.Domain` → `Domain/`; `MarqSpec.TradingCopilot.<Grouping>.ProjectB` → `<Grouping>/ProjectB/`. (Product projects only — not tools/test projects.)
- **Coverage & speed:** **every public method of every product class is unit-tested**; the full unit suite runs in **a few seconds** — fully mocked with FakeItEasy, no I/O, DB, network, or real waits.
- **Naming:** `MethodUnderTest_Should{ExpectedBehavior}_When{condition}` — the project convention; use this pattern for every test.
- **Integration tests → `MarqSpec.TradingCopilot.IntegrationTests`** (project structure mirrors `MarqSpec.TradingCopilot.UnitTests`). Nothing mocked; they verify components integrate end-to-end in two sub-tiers:
  - *Pre-Merge / PR Feedback (Fresh Test-Bootstrapped Compose Stack):* Venue-independent only — exercises API ↔ EF Core migrations ↔ TimescaleDB/pgvector ↔ domain logic in CI/dev using isolated temp volume mounts and seed scripts. Must **never** target or mutate an operator's persistent `db-data` volume. Continuously verifies that self-hosted single-operator compose deployments (ADR-0012/ADR-0015) remain healthy without cloud dependencies.
  - *Post-Merge Staging Verification:* Runs against **staging** post-merge to `staging` (§10) to verify real cloud infrastructure and venue integration before promotion to `main`.
  - Environment-specific values (account id / password, endpoints) are configurable per test category (integration vs. smoke) × environment (staging vs. production) — from CI secrets, never in source (§8).
- **Smoke tests = a tagged subset of the integration tests**, run against **production on deploy**. Production smoke tests are **strictly read-only** (e.g. verifying connectivity, contract resolution, account state) with zero live execution impact; execution-path checks belong to the staging integration suite; nothing execution-shaped receives the smoke tag. A smoke failure **flags the release for rollback**. Production deploy and any rollback are **human-approved** (§9, §10).
- **Test-first is the Definition of Done:** no new public method without a failing test written first; **bug fixes are regression-first**.
- **Every test guards a *named* failure mode** (boundary / invariant / regression) — happy-path-only suites don't pass review.
- **Safety-critical additions (net-new, highest rigor):**
  - **Deterministic replay:** drive suggestion generation, risk sizing, and execution-time re-validation against *recorded* market data so outcomes are reproducible (also underpins R-9 untaken-suggestion simulation, Q-5).
  - **Per-layer risk tests** (one test per rule): binding-constraint selection, resize-vs-block, and "no trade" emission for R-5/R-16.
  - **Auto-flatten (R-13):** simulate the close under partial fills, rejects, and connectivity loss at 2:59; assert positions end flat and the **"only reduces exposure"** invariant holds.
  - **Kill switch (R-11):** asserts every outbound order path is disabled and working orders cancelled.
  - **Phase-2 → live gate as tests:** the PRD §9 exit criteria become an executable checklist that must be green before live mode is enabled.

## 6. Agentic-AI Development Practices

- **Golden-set eval gate (planned — not built):** pinned model responses → **deterministic, repo-only, boolean** rubrics → a **PR-blocking gate** with a baseline and a max-regression bound. Trading rubrics (starting set): suggestion is fully specified (direction/entry/stop/target/size), rationale cites *real* signals present in context, computed size is within risk limits, session-clock/flatten deadline respected, no fabricated data.
- **Enforcement lives *below the model*.** Limits are enforced deterministically, never by prompt text: the **risk gate, re-validation, and sanity caps enforce — the LLM only proposes** (R-5/R-12/R-16). A fired risk/validity/flatten rule **hard-blocks** transmission, and the rule engine evaluates structured tool results, not model prose.
- **The three learning-goal seams stay inspectable and testable:** durable memory = the rulebook (R-7); verify-before-act = the execution gate (R-11/R-12); outcome feedback = the journal → engine loop (R-9).
- **Decide:** LLM-judge rubrics for subjective suggestion quality (deterministic rubrics first; defer these).

## 7. Observability, Monitoring & Alerting

- **Three pillars, one stack:** **OpenTelemetry** instrumentation → **Prometheus** (metrics), **Loki** (logs), and **Tempo** (traces), all viewed in **Grafana** — the self-hosted LGTM stack ([ADR-0002](adr/0002-observability.md)). Tempo is the tracing backend that makes end-to-end traces queryable.
- **End-to-end traces (the priority).** Every ingest is **one trace**: `websocket event → event-log append → processor → DB write`, and `REST poll → normalize → append → processor → DB write`. Because the event log is async, **trace context (`trace_id` / `span_id`) rides in the event envelope** and the consumer continues the trace via a **span link** — so one trace spans producer and consumer across the service boundary. This is the "websocket → record" / "poll → record" traceability we want; Tempo stores it and Grafana renders the waterfall with per-hop latency. The same traces cover the **suggestion path** — strategy agents → executor → suggestion (R-4) — so you can see which strategies contributed and where the time went. **Decided (gh#7):** context propagation is a single optional **W3C `traceparent`** field on the envelope (`EventDraft` / `EventEnvelope` / the `Events` column) — producers stamp it, consumers span-link to it; no separate `trace_id`/`span_id` fields.
- **Correlation across pillars.** Every log line carries `trace_id` / `span_id` (+ a correlation ID) so Grafana jumps **trace ↔ logs ↔ metrics** (Prometheus **exemplars** link a latency spike to its exact trace).
- **Metrics — health & performance.** Per-service **RED** (Rate / Errors / Duration — response-time **histograms** → p50/p95/p99), plus **runtime / performance counters** (GC, thread pool, heap, open connections/sockets) via OpenTelemetry runtime instrumentation + `System.Diagnostics.Metrics`. Availability from `/health` (liveness) and `/ready` (dependency checks), uptime, and **pipeline lag** (append→consume delay, DB write latency, ingestion gap/backfill events).
- **Execution-specific SLIs (net-new):** order-gate pass/block counts, **auto-flatten success and time-to-flat**, order-ack latency, suggestion and scan-alert latency (the §7 targets in the PRD).
- **Auto-flatten reliability is a monitored, *alertable* metric** — it must page. **Decided ([ADR-0019](adr/0019-alerting-channel-and-thresholds.md), `gh#242`):** **Pushover** behind an `INotificationChannel` seam, in **three layers** — the app's own direct push, Alertmanager rules, and an **out-of-process dead-man's switch** that pages when a check-in *fails to arrive*, because the worst R-13 failure is the host dying and taking the alerting with it. **Silence is the alarm.** Page on **`flatten.escalated`** (deadline + seconds), *not* `flatten.missed` — that fires 60 min late, after the prop backstop has already closed the position, and CL/GC have no backstop at all. A P1 is sent **once**; the repeat-until-acknowledged nagging is Pushover's, so the two never double-nag. Budget (PRD Q-12): **≤ 3 pushes/hour under any sustained fault, 0 on a clean session.**
- **AI usage & spend — a first-class tracked metric.** Every LLM invocation (ADR-0008) **and** every Cohere embed/rerank call records **tokens + estimated $ cost + latency**, traced ([ADR-0002](adr/0002-observability.md)) and aggregated in Prometheus/Grafana **by feature** (live suggestions, follow-ups, backtest runs, trigger triage, embeddings) and **model tier** (cheaper vs. top), daily/monthly. The **embed half is emitting** (gh#403): the `MarqSpec.TradingCopilot.Ai` meter records `ai.embed.{calls,tokens,cost_usd,latency}` by model and outcome on every call — a failover counts too, so a degrade is visible rather than an absence. The **LLM half now emits too** (gh#477): the same meter records `ai.llm.{calls,input_tokens,output_tokens,cost_usd,latency}` by model, tier and outcome, fed the per-call `AiCallCost` in the trigger scan alongside the ledger write (an escalated fire meters two, a `Failed` call meters at zero) — so Grafana shows **true total AI spend** (LLM + embed). It is **observability only**: a `System.Diagnostics.Metrics` meter is export-only, so it does not change the governor's in-app read (still the `AIUsage` ledger floor). The persisted **`AIUsage` row** (the in-app spend meter's source) **landed** (gh#431): the agent-review reviewer records one per-call token / cost / latency / outcome row, R-20-scoped to the firing owner. It is a **floor, not a complete accounting** — fail-open and lossy on host death — so the governor reconciles it against this aggregate meter rather than hard-capping on the ledger alone; a `Failed` call is a real zero-token row (billable latency), not an absence. This is the visibility behind the **AI-spend governor** (ADR-0008 — cap/throttle vs. budget) and the **Q-10** cost ceiling; a backtest reports its own $ cost. **Cost is the operator's own (ADR-0015):** you run the deployment and supply your own LLM + embeddings keys, so spend is **shown in the app** — cost per suggestion, cost per taken trade, cap remaining — *and* reported to **Grafana** for the operational view. The governor is a cap you set (gh#62). Spend was moved out of the UI under `gh#4` because one shared account funded many users; that premise is gone, so it comes back. (gh#4) **The Grafana half is delivered** (gh#412): the provisioned **AI usage & spend** dashboard reports total and 30-day spend, headroom against the daily cap, spend by **model tier** (so the ADR-0008 tiering bet is measurable), the LLM-vs-embeddings split, call outcomes, tokens in/out and latency with exemplar drill-through. Two limits are filed rather than hidden: headroom mirrors `Governor__DailyBudgetUsd` as a dashboard constant because Prometheus cannot read app config (gh#506 emits it as a gauge), and **per-feature** attribution awaits a `feature` tag on the LLM meter (gh#507) — until then the LLM/embed split is the feature axis, which is lossless today because every LLM row is `Feature = Triage`. The **in-app** surface remains Phase 4.

## 8. Deployment, Environments & Secrets

- **Deploy — build once, run everywhere ([ADR-0018](adr/0018-image-registry-ghcr.md)).** CI builds the multi-stage `Dockerfile` (sdk → aspnet, bind `$PORT`) **once per merge** and pushes it to **GHCR** (`ghcr.io/adammarquette/trading-copilot`, **public**), tagged by branch (`:develop`/`:staging`/`:main`) plus an immutable `:sha-<short>`. **Railway deploys that image** — the artifact CI built and tested, not a source rebuild. **Config/secrets are re-asserted from CI / Railway secrets on every deploy** — a self-healing "one source of truth" that prevents config drift; the **image itself carries no secrets** (they arrive from env at runtime), which is what makes it safe to publish public.
- **Local dev — `docker compose up`.** A checked-in root **`docker-compose.yml`** stands up the local environment with one command, **pulling the same GHCR image Railway runs** (`IMAGE_TAG` selects the build, default `:develop`) — no local rebuild ([ADR-0012](adr/0012-containerization-local-dev.md), [ADR-0018](adr/0018-image-registry-ghcr.md)). To run **your own changes**, layer **`docker-compose.dev.yml`** (`-f docker-compose.yml -f docker-compose.dev.yml up --build`), which builds from the working tree. The **database is config-driven**: the app's **connection string** comes from env / `appsettings` (`ConnectionStrings__*`), so it can use the compose DB service (TimescaleDB + pgvector, included for convenience), a local Postgres, or a managed instance. Local secrets live in a **gitignored `.env`** (copy `.env.example`); real secrets come from CI — never committed.
- **Environments track branches — dev / staging / prod:** the `develop` → `staging` → `main` promotion flow (§10) maps to three deployments. **Staging is a realistic test/review environment**, so features are exercised in production-like conditions before reaching production — nothing unreviewed touches prod.
- **Secrets server-side only:** ProjectX credentials and API keys live only in the cloud tier; the local UI never holds them (PRD §3). Also: **BFF server-side credential custody**, and **persisted DataProtection keys** if encrypted cookies must survive restarts.
- **Non-prod data comes from a production snapshot.** Staging/dev **seed and refresh their data stores from a snapshot of production ('live') data** for realistic history/context. The snapshot is *data only* — broker credentials stay per-environment secrets, so a snapshot can never hand a lower environment a live connection. **Decide:** snapshot refresh cadence + mechanism (ties to retention below).
- **Deployment environment vs. trading mode (R-14) — distinct axes, coupled by one safety policy:** **dev/staging are pinned to ProjectX practice accounts** (the real execution / auto-flatten path, practice money — never a live account); **production is the only environment permitted to run live**, where R-14's practice/live switch still governs the account. Staging therefore tests the *same* execution code that runs live (R-14 parity) with **zero real-money risk**. **Decide (before Phase 2):** practice/live → ProjectX credential/endpoint mapping within production (Q-4), and preventing an accidental live connection.
- **Retention — two windows.** The **event log** (ADR-0001) is a real-time pipeline with **short retention (< 24h, likely < 1h)**: its live data is augmented/superseded by the poller's **clean historical** (REST), so the log needn't persist. The **clean historical / time-series store** carries the **long** retention — the authoritative record and the source for full indicator rebuilds and R-9 replay (so **rebuild = reprocess the clean historical**, not replay the short event log). TimescaleDB handles both natively (retention policies, continuous aggregates, compression). Retention is **configurable** — a future event type may warrant longer. **Decide:** the exact windows + rollup cadence (vs. Q-10 cost).
- **Single-origin client.** The UI is a standalone local client against the remote BFF — one origin, standard cookies, no reverse-proxy needed for authentication.

## 9. Safety-Critical Engineering Discipline

The execution + auto-flatten layer moves real money and is **net-new / from scratch** — hold it to a higher bar than the rest of the system. The order-execution & risk-gate **model** this layer implements — one enforcing gate on every path, arm/edit/send, native vs. synthetic orders with an always-native safety stop, and the daily risk governor — is recorded in [ADR-0007](adr/0007-order-execution-model.md).

- **Fail-safe default:** when anything is uncertain, the safe state is **flat / no new orders**. Degrade deterministically; **never fabricate, never fail silently**.
- **Live is gated behind proven practice-account guardrails** (PRD §9): auto-flatten fires reliably, no unconfirmed or un-gated orders, native fills captured — *then* live is enabled with the same code, flipped mode.
- **Change control:** **Decide** a concrete policy for changes to the risk / execution / flatten / kill-switch paths — heightened review + mandatory safety suites (§5) before merge.
- **Auditability:** an immutable log of every order action and every guardrail decision (pairs with the proposed PRD security/audit requirement).
- **Human-approved production changes.** Deploying to production and rolling back are explicit **human-approved** actions, never automatic; a failed production **smoke test** (§5) flags the release for rollback. A person stays in the loop for anything that touches the live trading environment (§10).

## 10. Git Workflow, CI/CD & Definition of Done

- **Host: GitHub** (`adammarquette/trading-copilot`) — issues and pull requests.
- **Branching — `develop` → `staging` → `main`:** **`develop` is the sole integration branch**; all new work branches off it and PRs back into it. Promotion is one-way, with **exactly one allowed source per step**: `staging` accepts merges from **`develop` only** — any other source is an exception requiring a stated, good reason recorded in the PR — and `main` accepts merges from **`staging` only, with no exception**, so production history is single-source and every release traces back through staging (`staging` gets an escape hatch; `main` does not). Each long-lived branch deploys to its environment (§8). Never branch off or PR directly into `main`. **Name branches `<type>/<work-item-id>_<title>`** (`feature` | `bug` | `hotfix`; the tracking issue #; short kebab — e.g. `feature/42_risk-gate`), per [`CONTRIBUTING.md`](../CONTRIBUTING.md).
- **Issue-first — no orphaned PRs:** every PR references a tracking issue that states the problem/requirement, opened *before* the PR (`Closes #N` / `Related to #N`); if none exists yet, open one first. Issues and PRs are part of the knowledge base — cite them like doc sections (`gh#N`). Deployment work is tracked as GitHub issues.
- **Planning & progress: a GitHub [Project board](https://github.com/adammarquette/trading-copilot/projects)** guides planning and tracks progress; issues and PRs flow onto it. It is set up to span **multiple related repos**, so any companion repos added later (e.g. a client library) link to the same board and stay synchronized. Its **six-column funnel** (Backlog → Planning → Current ToDo → In Progress → Review → Done), the transitions, and the `work:*` + `Work Estimate: 1–5` tagging that routes work by role and model tier are governed by [`project-board-workflow.md`](project-board-workflow.md) (with the [Work Estimate rubric](work-estimate-rubric.md)).
- **Issue-first, then epics → tasks.** Every feature starts from a **defined issue** (before work begins). Group the work items for a goal or milestone under an **epic** — a GitHub **milestone**, or a parent/tracking **issue with sub-issues** — tracked on the Project board. Plan an epic by **decomposing it into tasks**, and where possible break the work down so **multiple agents can work in parallel**.
- **Dev + QA tasks per feature.** Each feature gets a **development task** and a **QA task**. **Development** writes the production code and its **unit tests** (test-first) — the Coding Agent contract (`src/AGENTS.md`). **QA** writes the **integration + smoke tests independently**, from the requirements rather than the implementation — the QA Agent contract (`src/MarqSpec.TradingCopilot.IntegrationTests/AGENTS.md`). They run in parallel; QA's independence verifies *intended* behavior and catches divergence between intent and code.
- **Commits & versioning:** Conventional Commits with an `Assisted-by:` trailer for AI-authored changes; commit *type* drives **SemVer**, `vMAJOR.MINOR.PATCH` tags on `main`. **Current version: `v0.1.0`** (pre-release; `0.x` = initial development per SemVer — anything may change). The version is asserted **here in prose** for now; a canonical `Version` property in `Directory.Build.props` (which exists but does not yet declare one) is still to wire.
- **Clean, coherent history — rebase-merge with curated commits; squash retired (gh#104).** A feature branch carries whatever commits it needs while in progress; before merge it is **curated with interactive rebase into understandable units of work** — each commit one reviewable package (Conventional type, coherent diff, a message that carries the why), because history is read *per commit* long after the PR is forgotten. PRs into `develop` land by **rebase-merge**, preserving those units; **squash-merge is disabled in the repo settings** (it flattened the units away). **True merge commits are reserved for the `develop → staging → main` promotions**, where preserving the promoted commits' exact SHAs keeps tested-artifact ≡ deployed-artifact literal. One mechanic to know: GitHub's rebase-merge still **re-creates the commits on the base** (new SHAs), so branch ancestry is *not* restored — the `stale-base` guard (gh#72) and **branch auto-delete on merge** (which makes GitHub auto-retarget stacked children) are what protect stacked PRs. **A second, and it is invisible where you would look for it (gh#562): a branch containing a merge commit is not rebaseable, so `mergeable` and `rebaseable` are different questions here.** When `develop` moves under an open PR, resolving it with `git merge origin/develop` leaves a merge commit on the branch — and GitHub cannot rebase across one, so **Rebase and merge** (the only method this repo allows into `develop`) greys out. The PR meanwhile reports `mergeable: true`, `mergeable_state: clean`, every required check green and nothing in the checks tab, exactly like the ruleset case above. **Check it explicitly** — `gh api repos/<owner>/<repo>/pulls/<n> --jq .rebaseable` — before calling a PR ready, and **prefer `git rebase origin/develop` over `git merge`** while a PR is open, which avoids creating the merge commit at all. To recover one that already has them: `git reset --soft origin/develop`, re-commit as the curated units, force-push — then **verify `git rev-parse HEAD^{tree}` is unchanged**, which proves the linearisation moved history without touching content. *(The root cause is `develop` churning under long-lived PRs; gh#357 tracks the merge-queue / strict-checks fix.)*
- **CI/CD via GitHub Actions:** stages **lint → build → test → publish image → deploy → verify**. On merge to a long-lived branch, CI **publishes the image to GHCR** (after unit tests pass; never on a PR) and Railway deploys that tag ([ADR-0018](adr/0018-image-registry-ghcr.md); the deploy hook itself is still to wire — runbook, *Operator setup*) — build once, run everywhere. Before a PR: `dotnet format --verify-no-changes` + unit tests green. Two guard rails: CI verifies tests *actually ran* (not a silent zero), and a license scan blocks restrictive-license bumps.
- **Test & deploy flow by environment:** integration tests (`MarqSpec.TradingCopilot.IntegrationTests`, §5) run in two sub-tiers: venue-independent API/DB integration runs in CI/dev against an **ephemeral real-Postgres container pre-merge** (Testcontainers on the compose DB image, `gh#121`) for early PR feedback, while full cloud and venue integration runs **against staging after a merge into `staging`**. **Production deploy is human-approved** (GitHub environment protection / required reviewer — the operator); on deploy, the **smoke subset** (strictly read-only on production) runs against production, and a smoke failure **flags the release for rollback** — rollback is human-approved too (§9).
- **Merge gate — enforced by rulesets (`gh#45`).** GitHub **rulesets** protect the long-lived branches: `develop`, `staging`, and `main` each require a pull request and green status checks before merge and block force-push / deletion — **a red check blocks the merge.** Required on all three: `build & unit tests` (format/build/unit), `integration tests (pre-merge)` (venue-independent QA on a throwaway real-Postgres container, `gh#121`), and `commit-hygiene` (Conventional / no leftover `fixup!`/`wip`, `gh#104`); plus `ladder` (`.github/workflows/branch-policy.yml`) on `staging`/`main`, which enforces the one-allowed-source-per-step promotion. Its `stale-base` sibling (`gh#72`) is **not** a required check — it is skipped on the long-lived branches, and requiring a never-running check would deadlock the merge; the same reason `publish image` (push-only) is excluded. Non-strict, **0 required approvals** (single operator), **no bypass** so the rules bind even for the admin. A further ruleset (`copilot-review-develop`) requires **Copilot to have responded** to a PR into `develop` — the findings are advisory, the response is not. Because a ruleset rule is **not a status check**, a PR awaiting it reads as blocked with every check green and nothing in the checks tab to point at; a quota-limited "unable to review" reply still satisfies it (runbook). This became possible when the repo went public (`gh#58`, `gh#45`); the rulesets live in repo settings, recorded in the [deployment runbook](deployment-runbook.md). Production deploy and any rollback remain **human-approved**. **A merge queue guards `develop` (`gh#357`)** — required checks prove a PR green against *its own base*, which says nothing about two PRs that are each green and break once both land (`gh#351`: different files, no git conflict, no run ever compiled the pair). The queue tests each PR **stacked on everything ahead of it** and merges only what stays green, so a PR can be rejected *after* passing its own checks — that is the mechanism working. Both workflows therefore trigger on `merge_group`, because a required check that never runs there deadlocks the queue; and the queue's merge method is **`Rebase`**, so `gh#104`'s "every branch commit becomes permanent history" survives. `staging`/`main` are not queued — each takes one curated source, so there is no combination to test. Setup and the enablement order: the runbook, *Merge queue*.
- **Docs move with the code — the same-PR rule.** A PR whose change touches documented behavior, the **data model** (data dictionary + its **mermaid ERD**), an API / contract, or the **UX** (wireframes) **updates those docs in the same PR**. Docs are the reconstructable memory (§11); letting them drift is a **defect, not a follow-up**, and a reviewer rejects a PR whose diff isn't reflected in them.
- **Definition of Done (starting point):** failing-test-first now green · standards/format clean · traces to a PRD requirement (`R-#`) and its tracking issue · tool/contract schemas updated on any interface change · **docs updated in the same PR (PRD / data-dictionary + ERD / wireframes / ADRs in lockstep)** · no secrets in source · **safety-critical paths carry their required suites (§5, §9)** · the eval gate (§6) passes **once it exists** — it is still unbuilt (no such workflow in `.github/workflows/`; the required checks are listed in §10), so today this clause binds nothing.

## 11. Companion Knowledge Wiki (development resource)

**This is not part of the trading platform.** It is a knowledge base that Adam (as the engineer) and the AI agents building the platform use *while developing it* — so the system can be built with real trading knowledge in mind rather than from assumptions. It sits alongside the project and informs design decisions; the running product does not read from it.

It can be stood up now, independent of the product build and its safety phasing — the earlier it exists, the more the design decisions are grounded as they're made. If a runtime knowledge base ever becomes a product feature, that is a separate decision — it would reuse this pattern but be specified as its own product requirement, with the trust-tier discipline below as a hard prerequisite.

> **The same pattern governs the project's own documentation** (README §*How we work — AI-Engineering first*): the `documentation/` layer — these files **plus the GitHub issues and PRs** — is the **highest-level source code of the platform**, abstracting the C# as C# abstracts machine code, kept compiling by the same-PR rule (§10) and navigated by its stable identifiers (`R-#`, ADRs, `gh#N`). The wiki below applies that discipline to *domain* knowledge; the rest of `documentation/` applies it to the *system itself* — both are written to be **recompiled from**, by agents or humans.

### What it is

A compounding knowledge base following Karpathy's LLM Wiki pattern: immutable **raw sources**, an **LLM-maintained wiki** of interlinked markdown (summaries, concept and entity pages, an evolving synthesis), and a **schema file** that makes the agent a disciplined maintainer rather than a generic chatbot. Three operations — **ingest, query, lint** — and two navigation files: a content-oriented `index.md` and a chronological, append-only `log.md`. Knowledge is compiled once and kept current, not re-derived on every question.

It lives under the project's `documentation/` folder (`documentation/wiki/`); the exact internal arrangement is left to implementation.

### What it holds

Domain knowledge that shapes *how the platform should behave*: trading methodologies, order-flow theory, instrument/product specifics, company financials, and design-relevant references. In practice this is what tells the engineer and the build agents what a good suggestion looks like, how order flow is read, how the risk layers should behave — the reasoning behind the product requirements, kept in one maintained place.

### Invariants

- **Dual-audience:** LLMs are first-class readers *and* writers (agents create and maintain pages), while the content stays fully **human-readable** — plain markdown, browsable in Obsidian or any editor. No format that trades legibility for machine convenience.
- **`index.md` + `log.md`** exist and follow the gist's guidelines: `index.md` is a one-line-per-page catalog updated every ingest and read first at query time; `log.md` is append-only with a consistent grep-able prefix (e.g., `## [YYYY-MM-DD] ingest | Title`).
- **Immutable raw sources:** the agent reads from the raw archive but never edits it.
- **A schema file** (e.g., `SCHEMA.md`) defines page types, citation conventions, the new-page-vs-edit heuristic, and the ingest/query/lint workflows; it co-evolves with use.
- **Folder structure is flexible** — the invariants above are what matter.

### Operations

- **Ingest.** A source dropped into an `ingest/` drop-zone is read by an agent that discusses key takeaways with Adam, writes a summary page, updates the index and relevant entity/concept pages, appends a log entry, and archives the raw source. One source may touch 10–15 pages. Default flow is one source at a time with Adam involved; batch ingest with lighter supervision is possible.
- **Query.** Ask questions against the wiki; the agent reads `index.md` first, drills into relevant pages, and answers with citations and trust tiers. Valuable answers can be filed back as new pages so explorations compound.
- **Lint.** A periodic health check flags contradictions, stale claims, orphan pages, missing cross-references, and concepts lacking a page. Drift is the pattern's top failure mode, so lint runs on a schedule, not only on demand.

### Trust tiers (worth the discipline)

Even as a development aid, the knowledge isn't uniform, and mixing tiers quietly corrupts judgment. Every page carries a verification status and a source-trust tier that travels with any citation: **authoritative** (filings, exchange specs), **curated** (vetted methodologies, Adam's own tested notes), and **unverified** (social/influencer, un-checked intake). Unverified material is quarantined — readable, but not citable as *grounds* for another page until checked against a primary source. This keeps a hype-video "methodology" from silently hardening into a design assumption, and it's the prerequisite that would make any future runtime use safe.

### Relationship to the product

It informs the PRD; it is not read by the built system. The three product subsystems it might be confused with stay separate: **soft-signal ingestion** (fast, ephemeral events), **the rulebook** (Adam's own trading rules, learned at runtime), and **the journal** (suggestion/trade outcomes) are all runtime product features — the wiki is none of these. It is design-time scaffolding.
