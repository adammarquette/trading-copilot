The order ticket — where it comes together

R-11 · R-5 · ADR-0007 the dock's Order tab · manual or armed from a suggestion — same panel
Built · gh#655: the arm → review → send core. Arming stages the order and returns the gate's decision without reaching the venue; sending is a separate action against the staged row, so what transmits is the approved size — re-sending the proposal is not a path the surface offers. A resize shows both numbers (asked-for and will-be-sent); the binding layer is named, not printed as the integer the wire carries; “no trade” is its own outcome rather than an order of zero; and each pre-gate refusal has its own message, read from the outcome since nothing was sized. TrailingStop is absent by construction — the send path refuses it, so a control for it would always fail. The safety stop is on every ticket: the floor rests at the venue, and “insured” should be readable rather than assumed.
Also built · gh#655: conditional entries (“send when conditions are met”) have since landed — see Send now — or when conditions are met below — and the armed-from-suggestion handoff: approving a suggestion arms a staged ticket and hands it to a review → send panel (the gate decision with the resize shown, then send or cancel; a real send is confirmed and acknowledged, not silently dismissed).
Also built · gh#828: editing an armed order in place — an operator who armed the wrong size amends the staged row instead of cancelling and re-arming. Every edit re-gates, and the decision on screen is the one the edit returned: what a later send transmits is the size approved on the edited row, never the arm's approval. The resize is measured against the edited ask, so a correct amendment does not report a resize that did not happen. Send is withdrawn while an edit is open — a typed-but-unapplied size is not what the server holds — and a refused edit changes nothing, so the armed decision stays exactly as it was. The safety stop is not on the form: the R-5 floor is not this surface's to move.
Also built · gh#828: the entry-action split button on the ticket's primary control — the operator's declared default (gh#218) acts on click, the other action sits in the menu. Defaulting to “send as-is” is practice-only, and the mode is re-checked at render rather than trusted from when the preference was written: a default declared while an account was practice is demoted out of the primary click once that account is live. It stays reachable from the menu — an explicit gesture — and the fast path skips the review, never the gate. The ticket falls back to plain Arm with no menu at all unless the roster vouches that the account is tradeable here — practice anywhere, live only in production, undeclared nowhere — so the one class this system refuses everywhere never sees a one-click send, and an account this environment may not trade is never offered a control that must fail. A menu whose entries cannot be vouched for is worse than no menu.
Not built yet: the blank manual ticket (its own entry form plus an instrument-spec / live-price read); the “Send now ▾” menu as drawn above, whose entry — send when conditions met — ships today as the checkbox rather than a menu item; and the Approve split on the suggestion card (see Taking a suggestion), which is blocked server-side: SuggestionTakeRequest carries only a reference price and the take always records ArmedTake, so “send this suggestion as-is” has no route that journals it honestly.

Far from the stop

The actual stop is synthetic / hidden — nothing rests on the book, so there's nothing to hunt. (Price is currently above entry.)

Within the band

Price comes within a configurable proximity of the stop (ticks / ATR / % of the entry→stop distance) → the actual stop is promoted to a native working order, now exchange-held for the moment it might fill.

Safety stop — always native

A catastrophic stop rests beyond the actual stop, always at the broker, placed at your configurable max drawdown per trade. It catches gaps, fast moves, and platform/connection outages — the position is never without a real stop, and its loss stays inside your account limits.

Managing working orders & positions — the live blotter

R-11 · R-13 · ADR-0007 the dock's Positions tab, expanded — see and act on what's resting or open
Built · gh#656the live blotter is built (Blotter.tsx): positions and resting orders from venue truth, each read tagged Live / Settlement / Unknown — and Unknown renders as unknown (never an empty table that would read as flat during an outage), with the empty-live view stated plainly. Per position it shows protection state (Protected / UNPROTECTED / unknown) from the resting protective legs. Cancel names the specific order (contract · size · price) and warns when it is protective, and it targets the journaled Order.Id the endpoint routes on — surfaced on the read alongside the venue key. A venue-spawned bracket leg carries no Order row (ADR-0007), so it shows no cancel / no reprice and reads "bracket leg — manage via its position" rather than a control that could not route. Reprice (the entry) is also built: it opens a small sheet that takes a new entry and the current market price — caller-supplied, since there is no server-side quote read — and the move re-gates below the model (R-16 fat-finger band, R-5/R-12); a refusal stays on the sheet with the gate's reason, and the safety stop is unchanged throughout. Exit is now built end to end (gh#656): POST /accounts/{id}/positions/{instrument}/exit reuses the same native-first ClosePositionAsync auto-flatten, the watchdog and the kill switch drive, and is deliberately not gated on the kill switch — that stops new risk, while closing what is already open must keep working. Only a verified flat is success: a close the venue accepted while it still reports exposure, and a venue that could not be reached, both surface as NOT done, because an operator told “closed” stops watching a position that may still be live. The confirmation names the position, its size and that it closes at market. Move stop is now built (gh#865 — see the note below). Reduce (a sized partial exit) now ships server-side (gh#928 — see the block below): the exit endpoint closes the whole position, the reduce endpoint part of it. Resize (gh#292) is the working-order size control, distinct from reducing a filled position. Live updates ride the realtime pushes (gh#649), re-reading venue truth rather than mutating local state.
Built · gh#865the Move stop control is built (Blotter.tsx) — an in-place move of the hidden working stop. It is offered only when the stop is Hidden (the read carries the staging): a Native stop rests at the venue, an Orphaned one re-arms on reconnect, and an order with no stop plan (the MES row, working coincident with safety) has no hidden stop — none of those show the control, and a venue-spawned leg (no Order row) never does. It opens a small sheet mirroring Reprice with one input — the new working stop — because a hidden re-stage is a local write, not an entry move, so it needs no market reference. The move is pre-validated strictly inside the safety → working → entry band (side inferred from the band's geometry, which the venue-truth read does not carry), and the safety stop is invariant; a move onto or past a bound is refused before the confirm enables. Client validation is UX only — the server re-validates the same band, the Hidden gate and any widen fail-closed, so a lost race (the stop promoted to a native venue order mid-edit) surfaces the server's refusal on the sheet rather than moving anything. On success it re-reads venue truth rather than assuming the move took. Backed by the read gh#865 inc 1 added (WorkingStopPrice / StopStaging / SafetyStopPrice / EntryPrice, all platform-held) over the existing gh#267 PATCH /orders/{id}/price re-stage. The unified “one sheet, the whole modify family” below stays the aspiration; the shipped control is a dedicated Move stop dialog beside Reprice.
Built · gh#928the Reduce endpoint is built server-side (POST /accounts/{id}/positions/{instrument}/reduce) — a sized partial close toward flat. It rides the venue's native sized partial close (IOrderExecutor.ReducePositionAsync, VenueCapability.ReducePosition), not an opposing order through the send ladder: a reduce lowers risk, and a gate refusing a risk-reducing action would be the wrong answer, so like the full exit it is not gated on the kill switch. It is strictly partial — a request at or beyond the open size is refused before the venue is touched (ExceedsPosition → 400), because reducing by the whole position is a full close, which belongs to the exit control that also cancels the protective OCO legs; a reduce can never silently become a bracket-stranding flatten. Only a verified reduction is success — verified against what was asked, not just direction: the outcome is read from venue truth after the attempt — the position smaller by exactly the requested amount is Reduced (200); anything else — less off than asked (a partial execution), more off (a stop or a concurrent exit fired, up to flat), the original size still standing, or a side flip — is NotReduced (409), and an unreachable venue Unreachable (409) — never a reduce. Known limitation, gated: the reduce leaves the attached protective bracket untouched — the ProjectX safety bracket carries no size field ({ticks, type}, sized to the fill; gh#293), so after a reduce the resting stop can over-cover the smaller position and, if it fires, overshoot toward a reversal. What ProjectX actually does to a position-linked bracket on a partial close is unverified here; the QA verification card gh#1012 is the hard pre-live gate before a funded account, exactly as gh#293 gated the resize (gh#292).
