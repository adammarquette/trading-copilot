# §10. Vectors & retrieval

Part of the [data dictionary](../data-dictionary.md) — see it for the ERD, the **Conventions** that
govern every domain, and the routing table. Cited elsewhere as **data dictionary §10**.

> **Storage codes:** `REL` relational · `TS` time-series (Timescale hypertable) · `VEC` vector.
> **Traces** cites the requirement (`R-#`), ADR, or `gh#N` the row answers to.

| Entity | Key fields | Storage | Traces |
|---|---|---|---|
| **Embedding** | owner type + id (suggestion / rule / soft-signal / snapshot / **topic**), vector, model (Cohere), created ts **Implemented** (gh#109, migration `AddEmbeddingStore`) as `EmbeddingRecord` / table `Embeddings`. Keyed on **owner kind + owner id + model** — model is IN the key because vectors from different models are not comparable, and the key doubles as the idempotence guard so a re-embed **updates** rather than appends (embedding is a paid call; re-ingestion is normal). Carries `Dimensions` and a `ContentHash` so an unchanged owner is recognised and the paid re-embed skipped. `vector(1024)` (Cohere embed-v3), **HNSW cosine** index. **Global / not `IUserOwned`** (R-20), following its owners. **Relational-only in the EF model** — `Vector` has no in-memory mapping, so coverage is integration-tier. **Skipped entirely where pgvector is unavailable** (gh#109 degrade: the app still starts, trading is unaffected, and the absence is declared rather than silent) — and since gh#474 the provider actually reports unavailable, so no embed is paid for a vector with nowhere to go. Providers: the keyless default ships here, Cohere in gh#403; first consumer gh#377. **Nearest-N read seam (gh#852, R-2):** retrieval ranks by `CosineDistance` (cosine distance in `[0,2]`; similarity = `1 - distance`) over the HNSW cosine index — `IEmbeddingRecall.NearestAsync(News, …)` = `.Where(OwnerKind = SoftSignal).OrderBy(CosineDistance).Take(n)` (it was `INewsEmbeddingSimilarity.NearestNewsAsync` until gh#1065 made the read kind-parameterised), served by a **partial** HNSW index over the soft-signal rows only (`IX_Embeddings_Vector_Cosine_SoftSignal`, migration `AddSoftSignalVectorIndex`, gh#864) — against the **table-wide** vector index Postgres may serve the `ORDER BY … LIMIT` from the HNSW graph and apply the owner kind as a **post-scan filter**, so a crowd of closer other-kind rows fills the approximate candidate window and the read returns **zero** neighbours though thousands exist (reproduced at 15,000 rows by gh#861); searching a soft-signal-only index leaves nothing for a post-filter to discard, so **this read's recall depends on that index existing**, and any other owner kind needing a vector-ordered read wants **its own** partial index rather than a shared table-wide one — its query-side caller (the shared retrieval pipeline, gh#995 / gh#1065) embeds the **query** with input type `search_query` (the write path embeds documents as `search_document`) and **degrades to an empty result** when the provider is unavailable, the query does not embed, or the read faults, so a consuming feed falls back and never errors. **Salience counterpart (gh#853, R-2/R-9):** `INewsEmbeddingSimilarity.GetVectorsAsync` reads back the stored `SoftSignal` vectors for a set of owners (a plain `Where(OwnerKind = SoftSignal).Where(ownerIds.Contains(OwnerId))` read, **no** `CosineDistance`), and `SemanticSalienceAxis` ranks the feed's **window candidates** in-process by **max cosine similarity** to the operator's **starred** vectors (nearest single star, clamped `[0,1]`) via the pure `EmbeddingSimilarity` helper — feeding the news feed's `SemanticEmbedding` axis (ADR-0014) and degrading to an empty axis on the same unavailable/fault conditions. Scoring the **known window candidates** (not a global nearest-set) is what keeps a recent near-a-star item from being starved, and it is two bounded reads, not one query per star. The vector **read** is relational-only like the write path, so the ranked read is **proven by QA #855** and `GetVectorsAsync` by a **paired QA card**, while the ranking math is **pure and unit-tested**. **Topic-match counterpart (gh#854, R-2):** the same polymorphic store gains an **`OwnerKind = Topic`** owner kind with **no migration** — the `OwnerKind` integer column's only constraint is `<> 0` and the PK `(OwnerKind, OwnerId, Model)` + indexes already admit any owner kind. The news-embedding pass also embeds each `NewsTopic` (name + keywords, keyed by topic name) as a `Topic` row against the **same** provider, per-pass spend tally and ledger; `INewsEmbeddingSimilarity.GetTopicVectorsAsync` reads them back — the topic analogue of `GetVectorsAsync`, a plain `Where(OwnerKind = Topic)` read — so the relevance pass matches a news vector to a topic vector in-process via the same pure `EmbeddingSimilarity` helper (kept a distinct seam method, not an owner-kind parameter, so the Domain seam carries no `Data` enum). Relational-only like the rest, so the topic embed + read are **proven by QA #877**. **Current-model reads (gh#881, gh#889):** **every** read — the by-owner `GetVectorsAsync` / `GetTopicVectorsAsync` **and** the ranked recall — filters `Model == provider.Model`. Cross-model vectors are not comparable, so pinning the current model makes `(OwnerKind, OwnerId)` unique in the by-owner result (the gh#854 last-wins collapse no longer picks an arbitrary model's vector), keeps every comparison same-model, and stops the ranked read ranking a retired-model vector or returning the same owner twice. After a model change an owner reads back empty until the embed pass re-embeds it under the current model — a self-healing degrade. The by-owner filter landed in gh#881; the `NearestNewsAsync` filter in gh#889, which had to land together with aligning the gh#864 recall guard (that guard drives `NearestNewsAsync` through a provider whose `Model` is `"none"`, so its seed model moves to `"none"` in the same PR — the model predicate is then a *second* post-scan filter on the HNSW window, so a migration window can narrow recall further than the owner-kind filter alone, still distance-ordered). gh#889 also **sweeps** the now-stale rows: on the success path, after a re-embed's current-model row is durably saved, a set-based delete removes that owner's `Model != current` rows (best-effort, no AI spend), so a completed model change leaves no duplicate-owner rows. Orphaned-owner rows — a deleted or renamed owner the incremental sweep can't reach — are **swept by a periodic anti-join GC** (`EmbeddingOrphanGcHost`, gh#902): per producer-backed owner kind (`SoftSignal` vs `News.DedupKey`, `Topic` vs `NewsTopics.Name`) an atomic `NOT EXISTS` delete off the hot path, **allow-listed** so producer-less kinds (`Suggestion` / `Rule` / `MarketSnapshot`) are never GC'd to zero. The **crash-leaked stale-model residual** — a `Model != current` row for an owner that **also** has a current-model row, missed by the incremental sweep after a crash — is swept by the **same host** (gh#915): one atomic self-`EXISTS` delete guarded by the current-model sibling, so an owner's sole vector (whatever its model) is never touched, and skipped when no provider is configured. This **closes** ADR-0001's deferred "full GC". **Cross-kind retrieval (gh#1065, R-6):** the store now carries two more owner kinds — **`Suggestion`** (its trade line + the model's rationale) and a new **`JournalEntry`** (a **closed** `Trade`, its trade line + realized result) — written by the same pass, with **no** column, key or constraint change (the gh#854 "new owner kind, no migration" property). What each new kind does need is its **own partial HNSW cosine index** (`IX_Embeddings_Vector_Cosine_Suggestion` / `..._JournalEntry`, migration `AddContextVectorIndexes`) — gh#864's rule, arriving at its first real test. The **ranked** read moved off `INewsEmbeddingSimilarity` onto **`IEmbeddingRecall.NearestAsync(kind, …)`** (the two by-owner reads stayed, and the old seam's name is now accurate); `PgVectorEmbeddingRecall` dispatches to **one query per kind with a literal owner kind**, because a partial index is matched against the query's predicate and a parameterised one would re-open gh#861's starvation silently. Ranking across kinds is meaningful because every kind reports the same cosine metric. **R-20 (gh#1065):** the store stays **global** — the owner-scoped kinds are scoped at the **hydrate**, read back through the tenant query filter, so a foreign row is absent and dropped exactly as a deleted owner is; on the **write** side a background host has no request user, so those scans `IgnoreQueryFilters` and each embed is ledgered to **that row's own owner** rather than `SystemOwner`. The orphan GC's allow-list gains both kinds (against `Suggestions.Id` / `Trades.Id`); `Rule` / `MarketSnapshot` stay off it, still producer-less | VEC | eng §2, R-2, R-4, R-6, R-8, R-9, R-20 |

> **Rerank (gh#975, R-2/R-6):** retrieval reranking is implemented behind the provider-neutral **`IReranker`** seam
> (Cohere `rerank-english-v3.0`), the cross-encoder counterpart of the `Embedding` write path's `IEmbeddingProvider`.
> It **stores nothing** — no entity, no migration — so it has no row above; it **degrades to a passthrough
> (identity-order) result rather than throwing**, meters every call on the `MarqSpec.TradingCopilot.Ai` meter, and
> prices per **search** from a single pinned `CohereOptions` rate (ADR-0008). **First consumer: the read-only
> `search_news` chat tool (gh#987)** — it embeds the query, recalls the nearest news, hydrates
> the text, and reranks the candidates, reading the returned **list order** (authoritative on both the reranked and
> the passthrough path). It ledgers the rerank call under `AiUsageFeature.Chat` (and the query-embed under `Embed`)
> stamped to the operator (ADR-0008) — the deferred first consumer the gh#975 seam landed ahead of, exactly as
> gh#377 was for the embed ledger write. **Shared into a pipeline (gh#995, ADR-0027):** that embed → recall → hydrate
> → rerank flow was extracted into one scoped, read-only pipeline (then named `INewsRetrievalService`) — the
> `search_news` tool became a thin adapter over it, and **always-on chat grounding** its **second consumer**, retrieving
> news for **every** chat turn as
> untrusted **user-role** context (placed on the operator's final turn, **never** the system prompt) and ledgering the
> same `Embed` + `Chat` spend stamped to the operator. One pipeline, two callers, rather than two drifting copies; the
> grounding it feeds is **ephemeral** (§12 — read each turn, persisted nowhere). **Generalised cross-kind (gh#1065):**
> that pipeline is now **`IContextRetrievalService`** — one query-embed, a recall **per asked kind**, a hydrate
> each, a merge **nearest-first across kinds**, and **one** rerank over the merged set (capped at the same ceiling
> one kind gets, so adding a kind never grows the rerank payload). A keyless deployment still degrades to that
> merge order rather than to "all news, then all suggestions". Always-on chat grounding asks for **every** kind;
> `search_news` deliberately still asks for news only, because its name and description are a contract with the
> model about what it returns.
